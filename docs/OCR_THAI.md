# ภาษาไทยกับ PaddleOCR — สิ่งที่อ่านได้และอ่านไม่ได้

เอกสารนี้บันทึกข้อจำกัดที่สำคัญที่สุดของระบบ และหลักฐานที่วัดได้จริง
เพื่อให้คนที่มาดูทีหลังไม่ต้องเสียเวลาค้นหาสาเหตุซ้ำ

## ข้อเท็จจริง

**PaddleOCR 2.9.1 ไม่มีโมเดลสำหรับภาษาไทย**

```python
>>> PaddleOCR(lang="th")
AssertionError: param lang must in dict_keys(['ch', 'en', 'korean', 'japan',
'chinese_cht', 'ta', 'te', 'ka', 'latin', 'arabic', 'cyrillic', 'devanagari'])
```

`OCR_LANGUAGE=th` ซึ่งเป็นค่าที่ติดมาจากโปรเจกต์ต้นทาง จะทำให้ engine
โหลดไม่ขึ้นเลย ค่าปริยายของโปรเจกต์นี้จึงเป็น **`latin`**

## ผลที่ตามมา

เอกสารที่ระบบนี้อ่าน (แบบ ร.ว.จ ๗/๔, บ.ว.จ ๗/๔-ขพ, ร.ค.-๔)
เป็นฟอร์มพิมพ์ที่**เขียนด้วยลายมือ** ซึ่งมีทั้งอักษรละตินและอักษรไทยปนกัน

| สิ่งที่อยู่ในช่อง | ตัวอักษร | ผลจาก `latin` |
| --- | --- | --- |
| ชื่อยา / ความแรง — `Lorazepam 1 mg` | ละติน | อ่านได้ ค่อนข้างดี |
| ชื่อการค้า — `Lorazep` | ละติน | อ่านได้ดี |
| เลขที่รุ่นผลิต — `T25275` | ละติน+เลข | อ่านได้ดี |
| ยอดยกมา / รับ / จ่าย / คงเหลือ | เลข | อ่านได้ดี |
| วัน เดือน ปี — `16/3/69` | เลข | อ่านได้บ้าง เส้นทับขีด `/` หายบ่อย |
| ชื่อผู้รับยา — `ชลิดา จันทร์สด` | **ไทย** | **อ่านไม่ได้** |
| หน่วย — `เม็ด` | **ไทย** | **อ่านไม่ได้** |
| หมายเหตุ | **ไทย** | **อ่านไม่ได้** |
| หัวตารางที่พิมพ์มา | **ไทย** | **อ่านไม่ได้** |

## กับดักที่ต้องระวัง

ช่องภาษาไทย**ไม่ได้คืนค่าว่างหรือสัญลักษณ์มั่ว** โมเดล latin
ตอบกลับมาเป็นตัวอักษรละตินที่ดูสมเหตุสมผล:

```
"ชลิดา จันทร์สด"   ->  "t@on SunScQ"
"หมายเหตุ"         ->  "n&nan"
"ไพเนตร บุตรดีสา"  ->  "1wsu6yo1ssp"
```

จึงเป็นไปไม่ได้ที่จะดูจากตัวข้อความแล้วบอกว่าช่องนี้อ่านสำเร็จหรือไม่
`"t@on SunScQ"` หน้าตาไม่ต่างจากชื่อที่อ่านถูกจริง ๆ

ระบบนี้จึงเตือนตาม**คอลัมน์ ไม่ใช่ตามเนื้อหา** — ดู `form_layout.THAI_ROLES`
ทุกแถวที่มีข้อมูลในคอลัมน์เหล่านั้นจะถูกตั้ง `needs_review = true`
พร้อมเหตุผล `"... is written in Thai, which this engine cannot read"`

> อย่าเขียนฟังก์ชันที่พยายามเดาว่าข้อความไหน "ดูมั่ว" แล้วใช้มันคัดช่องไทย
> มันใช้ไม่ได้ และเคยพยายามมาแล้ว — ดู `balance_normalizer.looks_unreadable`
> ซึ่งตอนนี้ใช้คัดเฉพาะเศษหมึก/เส้นตารางที่หลุดมาเป็นข้อความเท่านั้น

## ผลกระทบต่อหัวฟอร์ม

หัวฟอร์มเหนือตาราง (ชื่อผู้รับอนุญาต, ชื่อสถานที่, ที่ตั้ง, จังหวัด,
ใบอนุญาตเลขที่) เป็นภาษาไทยทั้งหมด จึงอ่านไม่ได้เช่นกัน
นี่คือเหตุผลที่คอลัมน์ `ชื่อสถานพยาบาล`, `ที่ตั้ง`, `จังหวัด`,
`ผู้ดำเนินกิจการ` และ `เลขที่ใบอนุญาต` ในไฟล์ output ออกมาว่าง
ไม่ใช่เพราะการสกัดพลาด

ข้อความดิบที่อ่านได้เหนือตารางยังถูกเก็บไว้ใน `PageParse.header_text`
เผื่อวันหนึ่งมีโมเดลไทยแล้วย้อนกลับมาอ่านใหม่ได้

## การระบุชนิดฟอร์ม

เพราะหัวตารางอ่านไม่ได้ ระบบจึงระบุชนิดฟอร์มจาก**สัดส่วนความกว้างคอลัมน์**
ที่ตรวจจับจากเส้นตารางจริง แทนการอ่านชื่อฟอร์ม — ดู `workers/form_layout.py`
วิธีนี้แม่น 8/8 หน้าบนเอกสารตัวอย่าง และไม่ขึ้นกับภาษาเลย

## ถ้าต้องการให้อ่านภาษาไทยได้

เรียงตามความคุ้มค่า:

1. **เปลี่ยน engine** — `workers/ocr_engine.py` ถูกเรียกผ่าน
   `recognize_image(image)` เพียงจุดเดียวจาก `balance_parser` การเปลี่ยนไปใช้
   engine อื่น (Typhoon OCR, Google Vision, Azure Document Intelligence,
   vision-LLM) แก้แค่ไฟล์นั้นไฟล์เดียว ส่วน grid detection / การแบ่งแถว /
   การ map คอลัมน์ / export ใช้ต่อได้ทั้งหมด
2. **อัปเกรด PaddleOCR เป็น 3.x** แล้วตรวจว่ามีโมเดลไทยหรือยัง
3. **เทรนโมเดล rec ภาษาไทยเอง** — แพงที่สุด และลายมือยิ่งยาก

เมื่อใดที่ engine อ่านไทยได้ ให้เพิ่มรหัสภาษานั้นลงใน
`form_layout.THAI_CAPABLE_LANGUAGES` แล้วการเตือนรายคอลัมน์จะหยุดเอง

## ข้อควรรู้เรื่องลายมือ

ต่อให้มีโมเดลไทย โมเดลของ PaddleOCR เป็นโมเดลสำหรับ**ตัวพิมพ์**
ความแม่นกับลายมือจะต่ำกว่าอยู่ดี

ตัวเลขที่วัดได้จริงจาก `ข้อมูล OCR.PDF` (8 หน้า, สกัดได้ 35 แถว, 200 dpi):

| ตัวชี้วัด | ผล |
| --- | --- |
| ระบุชนิดฟอร์มถูก | 8/8 หน้า |
| ชื่อยาอ่านได้ | 33/35 แถว |
| เลขที่รุ่นผลิตอยู่ในรูปแบบที่คาด | 29/35 แถว |
| **วันที่อ่านได้** | **10/35 แถว** |
| แถวที่ตรวจยอดได้ (มีทั้งยอดยกมาและคงเหลือ) | 19/35 แถว |
| ในจำนวนนั้น ยอดลงตัว | 11/19 แถว |
| ความมั่นใจเฉลี่ยรายหน้า | 0.72 – 0.80 |
| **แถวที่ถูกตั้ง `needs_review`** | **35/35 แถว** |

เหตุผลที่ถูกเตือน เรียงตามจำนวน:

| จำนวน | เหตุผล |
| --- | --- |
| 25 | วันที่อ่านไม่ได้ |
| 20 | ช่องผู้รับยาเป็นภาษาไทย |
| 12 | คงเหลืออ่านเป็นตัวเลขไม่ได้ |
| 8 | ยอดไม่ลงตัว |
| 6 | วันที่ต้องเดาจากช่องที่ไม่ชัด |
| 6 | เลขที่รุ่นผลิตผิดรูปแบบ |

วันที่เป็นจุดอ่อนที่สุด เพราะขีด `/` ที่คั่น วัน/เดือน/ปี เป็นเส้นบางที่
detector มักไม่จับ ทำให้ `16/3/69` กลายเป็น `173169` แล้วแยกกลับไม่ได้
(`balance_normalizer._split_digits` จะยอมแยกเฉพาะกรณีที่แยกได้ทางเดียวเท่านั้น
ถ้ากำกวมจะคืนค่าว่างพร้อมเตือน ดีกว่าเดาแล้วผิด)

การตรวจสอบยอด (`ยอดยกมา + รับ − จ่าย = คงเหลือ`) คือเครื่องมือที่ดีที่สุดที่มี
เพราะเป็นการยืนยันตัวเลขสี่ช่องด้วยกันเองโดยไม่ต้องพึ่งข้อมูลภายนอก —
ดู `balance_parser._check_balance`

**สรุป: ผลลัพธ์ชุดนี้ต้องผ่านสายตาคนก่อนนำไปใช้** ระบบออกแบบให้บอกได้ว่า
แถวไหนน่าเชื่อถือ (`needs_review = false`) ไม่ได้ออกแบบให้เชื่อได้ทั้งหมด
